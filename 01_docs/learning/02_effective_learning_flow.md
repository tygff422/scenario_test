# 02_effective_learning_flow

- 日付: 2026-08-22
- 関連: [ai_workflow/01](../ai_workflow/01_verification_and_collaboration_balance.md)（AIとの協働の型、③で決定済み）
- 位置づけ: ③がAIとの協働プロセス（誰がどう進めるか）の話なのに対し、こちらは**学習方法論そのもの**——実装を通してどう学ぶと効率的に定着するか。具体的に何を実装するか（Audio等）は`decisions/`・`known_issues.md`側で扱う。

## 背景

③で「①〜④説明→確認→⑤実装→理解度確認」という協働の型は決まった。この型の中に、学習として効果が高いとされる要素をどう組み込むかを整理する。

## 5つの原則

### 1. 比較学習を意図的に組み込む

新しいものを学ぶ時、単体で理解しようとせず既存の実装と比べる。1つの実例だけだと「たまたまそうなってる」のか「本質的にそうあるべき」なのか区別がつかない。2つ目の実例が出て初めて「これがパターンなんだ」と分かる。

```text
悪い例：「AudioAdapterってこういうものです」で終わる
良い例：「CameraAdapterのsetup()とAudioAdapterのsetup()、何が同じで何が違う？」を都度聞く
```

### 2. ミニマル→実物、の順で理解する

いきなり複雑な実装（実機カメラ等）で新しい概念を学ぶと、本質と枝葉が混ざって理解しづらい。新しい技術要素が出てくる時だけ、先にミニマルな例（コードスニペット程度で良い）で概念を掴んでから実物に適用する。

### 3. 「詰まった/バグった経験」を資産として扱う

LED二重チェックのバグ、`normalizer`がインストールされなかった件など、失敗したから学べたことがある。バグを直したら終わりにせず、「なぜ起きたか」「次に同じ間違いをしないための一般化した教訓」まで一言添える（`decisions/`に既にこの習慣がある）。

### 4. 理解確認は「説明」だけでなく「応用」まで

説明できることと応用できることの間には差がある。

```text
説明できるかの確認：「setupとteardownの役割の違い、説明できる？」
応用できるかの確認：「じゃあFileAdapter作るとしたら、setupは何をする？」
```

後者まで確認できて、初めて「理解した」と言える。

### 5. 定期的な振り返りをルール化する

都度の理解確認（4）とは別に、ある程度まとまった単位（例：1つのAdapter作り終わるごと）で振り返りの機会を設ける。今回①②③をまとめて棚卸ししたこの会話自体が、この手法の実践例。

## CLAUDE.mdへの反映（2026-08-22、案C採用）

常時効くもの（1. 比較学習、4. 応用確認）だけをCLAUDE.md本文の「実装後、理解度を確認する」に溶け込ませた。状況次第で参照すれば良いもの（2. ミニマル先行、3. バグの資産化、5. 定期振り返り）は詳細をこのファイルに残し、CLAUDE.mdからはリンクのみとした（CLAUDE.md自体の肥大化・情報量過多を防ぐため）。

あわせて、CLAUDE.md自体を実装しながら継続的に改善して良いというルールも追加した（「CLAUDE.mdの継続的な改善」セクション）。
