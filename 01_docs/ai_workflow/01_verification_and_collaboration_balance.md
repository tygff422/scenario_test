# 01_verification_and_collaboration_balance

- 日付: 2026-08-22
- 位置づけ: `decisions/`（このプロジェクトの設計判断）・`learning/`（ユーザー個人のスキル）のどちらとも異なり、**Claudeとの協働プロセス自体**について振り返り・課題を溜めていく場所。他のプロジェクトでAIと協働する際にも応用できる可能性がある内容。

## 背景

このプロジェクトを通じて、AIが実装した機能が「作った後、しばらく経ってから実は動いていなかった」と判明するケースが繰り返し発生した。この協働の進め方自体を振り返る。

## 課題

- [ ] **検証が常に後手に回っていた**：以下4件はいずれも「機能を実装 → しばらく経ってから改めて確認したら実は動いていなかった」というパターンで発覚した
  - 正規の実行入口（`run_scenario.py`）が存在しなかった
  - `GenericOrchestrator`が実機カメラで一度も検証されていなかった（Step5〜7の変更が全て未検証のまま積み上がっていた）
  - LED判定が二重に実行されるバグ（`CameraAdapter.setup()`と`Orchestrator.execute()`の重複）
  - 撮影画像・実行ログが実際には保存されていなかった

  理想は「機能を作ったら、その場ですぐ実機・実データで1回検証する」習慣だが、今回は後からまとめて棚卸しする形になった。
- [ ] **「AIが実装したから動くはず」という前提で進んでしまった箇所が複数あった**：上記の後手検証と表裏一体。AIの実装結果を鵜呑みにせず、都度小さく検証する頻度をどう上げるかが課題
- [ ] **AIに実装を任せる範囲と学習目的のバランスが未確定**：「設計する力を身につける」ことが目的なのに、実装コードの大半はClaudeが書いた。一度この点について相談し、「Claudeが実装するが設計判断は都度確認する」という進め方に調整したが、それでもタイピングして手を動かす経験は増えていない（[learning/01](../learning/01_remaining_skillup_tasks.md)参照）。目的に対して、どこまでAIに実装させるのが適切かの方針がまだ定まっていない

## 今後の進め方（案、未確定）

- 機能追加のたびに「作った直後に小さく検証する」をルール化するか
- 実装をAIに任せる範囲と、ユーザー自身が書く範囲の線引きをどうするか

次回の相談で具体的な方針を決める。
