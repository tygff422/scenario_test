# 01_verification_and_collaboration_balance

- 日付: 2026-08-22
- 位置づけ: `decisions/`（このプロジェクトの設計判断）・`learning/`（ユーザー個人のスキル）のどちらとも異なり、**Claudeとの協働プロセス自体**について振り返り・課題を溜めていく場所。他のプロジェクトでAIと協働する際にも応用できる可能性がある内容。`known_issues.md`と同じ「決まってること／決まってないこと／問題点／改善案」形式で整理している。

## 背景

このプロジェクトを通じて、AIが実装した機能が「作った後、しばらく経ってから実は動いていなかった」と判明するケースが繰り返し発生した。さらに、実装内容・実装箇所を利用者側が把握できていない、という理解度そのものの危機感が指摘され、根本原因は「確認を挟まず自律的に進める」という運用方針にあると判明した。この協働の進め方自体を振り返る。

## 1. 検証が常に後手に回っていた

- [x] 対応方針決定（2026-08-22、CLAUDE.md更新）
- **決まってること**：以下4件はいずれも「機能を実装 → しばらく経ってから改めて確認したら実は動いていなかった」というパターンで発覚した
  - 正規の実行入口（`run_scenario.py`）が存在しなかった
  - `GenericOrchestrator`が実機カメラで一度も検証されていなかった（Step5〜7の変更が全て未検証のまま積み上がっていた）
  - LED判定が二重に実行されるバグ（`CameraAdapter.setup()`と`Orchestrator.execute()`の重複）
  - 撮影画像・実行ログが実際には保存されていなかった
- **決まってないこと**：新しい運用（後述）を実際に回してみて、効果があるか
- **問題点**：機能を作ったらその場ですぐ実機・実データで1回検証する、という習慣が無く、後からまとめて棚卸しする形になっていた
- **改善案（採用）**：CLAUDE.mdに「実装作業の説明順序」を追加。実装コードを伴う作業では①設計全体像→②現時点の立ち位置→③実装意図→④実装箇所（フォルダ/ファイル）まで説明した時点で一旦止まり、認識を確認してから実装に進む運用に変更した

## 2. 「AIが実装したから動くはず」という前提

- [x] 対応方針決定（2026-08-22、CLAUDE.md更新。1と同じ対応）
- **決まってること**：この前提で進んでしまった実例（1の4件）は特定済み
- **決まってないこと**：実際に運用してみて、この前提に頼らずに済むようになるか
- **問題点**：「Fakeでテストが通った」ことと「実機で本当に動く」ことを混同しやすい構造的な問題。実際、Fakeテストは全部通っていたのに実機では未検証のまま積み上がってた
- **改善案（採用）**：1と同じ、実装箇所まで説明→確認のステップを挟むことで、実装内容をその都度利用者が把握し、鵜呑みにするリスクを下げる

## 3. AIに実装を任せる範囲と学習目的のバランス

- [ ] 未対応（引き続き検討中）
- **決まってること**：「Claudeが実装するが、設計判断は都度確認する」という進め方に一度調整した経緯がある。さらに2026-08-22、実装コードを伴う作業には「実装箇所まで説明してから確認する」ステップを追加した（1・2の対応と同じ）
- **決まってないこと**：「どこまでAIに任せるか」の具体的な線引き（骨格はClaude・ロジックはユーザー、等のハイブリッド方式を試すかどうか）
- **問題点**：「設計は相談してるから良し」で進めてきたが、結果的にタイピングして手を動かす経験は増えていない。目的（[learning/01](../learning/01_remaining_skillup_tasks.md)のスキルアップ）に対して、今の運用が最適化されてるとは言い難い
- **改善案**：a) 次の新機能（Audio等）で「骨格はClaudeが用意、ロジックはユーザーが書く」ハイブリッド方式を試す　b) 完全にユーザーが書き、Claudeはレビュー・質問対応のみに徹する　c) 現状維持

## 根本原因の整理（2026-08-22）

1・2の問題は、突き詰めると「確認を挟まず自律的に進める」という運用方針そのものが原因だった。これが、①情報量過多、②説明の分かりづらさ（特に実装箇所の説明漏れ）、③一方通行の対話、④「勝手にやってる」という当事者感の喪失、⑤消化時間の不足、という5つの症状を引き起こしていたと整理できた。CLAUDE.mdの「実装作業の説明順序」追加は、この根本原因への対応。3（実装分担の線引き）は、この新しい運用を実際に試してから改めて判断する。
